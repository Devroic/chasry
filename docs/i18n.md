# Internationalization (i18n)

Read this before adding a new translated surface, a new Server Action validation message, or
touching `lib/locale.ts` / `i18n/request.ts`.

`next-intl`, in **cookie-based locale mode**, not the library's URL-segment routing.

- `lib/locale.ts` — pure constants only (`LOCALES = ["en", "el"]`, `DEFAULT_LOCALE`,
  `LOCALE_COOKIE`, `LOCALE_LABELS`). **Must never import `next/headers`** — it's pulled in by the
  Client Component `LanguageSwitcher`, and a server-only import there breaks the production
  build. Put server-only locale helpers in `i18n/request.ts` or a call site instead.
- `i18n/request.ts` — the `next-intl` plugin config, reads the `chasry_locale` cookie
  server-side, falls back to `DEFAULT_LOCALE`, dynamically imports `messages/{locale}.json`.
- `lib/locale-actions.ts` — `setLocale(locale)`: validates, sets the cookie (`path: "/"`, 1-year
  `maxAge`, `sameSite: "lax"`), `revalidatePath("/", "layout")`.
- Root `app/layout.tsx` wraps `children` in `<NextIntlClientProvider messages={messages}>` with
  the **full** messages object, so any Client Component can call `useTranslations()` without
  extra provider wiring.
- `messages/en.json` / `messages/el.json`, namespaced by feature area. Uses ICU plural rules and
  rich-text tags (`t.rich()`) directly rather than app-side string-building, so translators can
  reorder words per language.
- Server Components call `getTranslations()` (awaited); Client Components call
  `useTranslations()`. A component only needs to become `async` for this if it's never rendered
  from a Client Component, check that before converting a new one, if it is, translate at the
  call site instead and keep the leaf component's props as plain strings, or accept a translator
  as a prop (the pattern `describeReminderSchedule` uses).
- An `async` Server Component (like `SiteFooter`) can't be instantiated inline from a Client
  Component. `app/(dashboard)/layout.tsx` renders `<SiteFooter />` itself and passes it into
  `DashboardShell` as a `footer` prop instead.
- Every `lib/validations/*.ts` schema is a **function that takes a `Translator`**
  (`lib/validations/shared.ts`) and returns the Zod object, instead of a static export, so
  validation messages are localized both client-side (`zodResolver`) and server-side (re-
  validation inside the Server Action). Call sites read `schemaName(t)`, and
  `z.infer<typeof schemaName>` becomes `z.infer<ReturnType<typeof schemaName>>`.
  A **global Zod error map is deliberately not used**: it would be process-wide mutable
  module-level state, and this app is a single Node process serving every locale concurrently,
  a shared mutable error map would leak one visitor's language into another's response under
  concurrent load. Pass `t` explicitly into each schema call instead.
  Server Actions that throw rather than return an error (e.g. `reopenInvoice`'s free-plan-limit
  check) must translate the message **before** throwing, server-side.
- **Deliberately, permanently English-only**: `/terms` and `/privacy` body content, legal text
  carries real risk if a translation subtly gets a term wrong. The `SiteHeader`/`SiteFooter`/
  `BackLink` chrome around both pages stays fully translated.
